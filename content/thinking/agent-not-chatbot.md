<p>「Agent」是这两年 AI 产品里最容易被滥用的词：接一个大模型、加几个工具调用、写一句「自主规划」，就敢叫 Agent。判断一个产品是不是 Agent，我从不看它接了什么模型、有几个工具，只看一件事——<strong>把对话界面拿掉，这个任务还能不能完成？</strong></p>

      <h2>判断 Agent 的三个标准</h2>
      <p><strong>感知环境。</strong>它需要的信息，是用户口述的，还是它自己去拿的？读文件、查数据、看页面状态、调接口——「自己拿到完成任务所需的信息」是第一步。只会等用户把一切喂给它的，仍然是聊天机器人。</p>
      <p><strong>拆解与决策。</strong>它能不能决定下一步？包括决定「信息不够，先问一句」和「这条路走不通，换一条」。只会按固定顺序执行的，是脚本，不是 Agent。</p>
      <p><strong>调用工具并交付。</strong>结果有没有落回用户的工作对象——草稿、文件、表格、工单、日程？还是只停在聊天框里一段文本？</p>
      <p>有一个很省事的反向检验：去掉对话框。如果任务完不成，那它是 Chatbot 加了工具调用；如果任务还能完成，对话只是入口之一。一句话总结：<strong>Chatbot 交付「回答」，Agent 交付「结果」。</strong>用户愿意付钱的从来不是回答，是结果。</p>

      <h2>案例：GEO 内容生产的交付物不是一篇文章</h2>
      <p>我做源引 GEO 时，第一版设计其实是「输入品牌 → 输出文章」的生成器，本质是一个会写长文的 Chatbot：用户填品牌资料，点生成，拿到一篇文章，复制走。</p>
      <p>但用户的真实目标是「品牌在 AI 答案里被正确描述、被提及」，文章只是中间产物。只交付文章，用户还得自己判断该写什么、发到哪里、有没有用——任务没有闭环。</p>
      <p>后来我把任务拆成四段，每段都配工具和验收：</p>
      <div class="diagram">
        <p class="diagram-title">GEO 任务闭环 · 四段交付</p>
        <div class="flow-chain">
          <div class="flow-step"><span class="idx">01 诊断</span><b>为什么没被提到</b><span>工具：读真实提问与竞品提及；输出可归因的结论与行动项</span></div>
          <div class="flow-step"><span class="idx">02 策略</span><b>该写什么</b><span>工具：从买家问法生成选题；输出内容类型、结构与证据要求</span></div>
          <div class="flow-step"><span class="idx">03 生产</span><b>做成可用的稿</b><span>工具：预检、生成、质量门禁、同步到平台草稿箱</span></div>
          <div class="flow-step"><span class="idx">04 回测</span><b>有没有用</b><span>工具：真人提问、留存原始回答与引用证据，回填下一轮</span></div>
        </div>
      </div>
      <p>交付物因此变了：不是一篇文章，而是「文章 + 为什么这么写 + 发布后的实测记录 + 下一轮要改什么」。用户拿到的是可以继续行动的闭环，而不是一段需要自己判断的文本。</p>
      <p>这个拆法带来三个后果：一是每一步都要工具（召回、平台同步、探针实测），不是纯生成；二是每一步都要验收标准，内容不合格要打回；三是产品指标和用户目标必须对齐——我不承诺「被引用」，只提供可回测的记录。生成式答案有随机性，把单次结果当结论，就是在制造期望债。</p>
      <p>项目在 2026.10 阶段性中止了，原因是效果与商业化未达预期。但它验证了一件事：Agent 产品的设计单位是「任务」，不是「对话轮次」。</p>

      <h2>失败兜底才是 Agent 产品的核心设计</h2>
      <p>Demo 里的 Agent 只在成功路径上跑，产品里大部分设计工作发生在失败路径上。Agent 的失败往往不是「答错了」，而是「任务停在半路，用户不知道发生了什么」。</p>
      <div class="decisions">
        <div class="decision"><b>工具失败</b><p>API 超时、权限过期、页面改版。产品要能重试、降级、提示用户手动接管，而不是弹一个报错就结束。</p></div>
        <div class="decision"><b>信息不足</b><p>用户没给关键资料，模型只能编。产品要能停下来问，而不是硬着头皮输出一份看起来很完整的结果。</p></div>
        <div class="decision"><b>质量不合格</b><p>结果看起来对、实际用不了。要有门禁和打回机制：宁可不出，也不出错。</p></div>
        <div class="decision"><b>成本失控</b><p>重试和工具调用深度放大，一次任务花掉十次的钱。要有预算上限，并把成本显示出来。</p></div>
      </div>
      <p>我判断一个 Agent 产品是否成熟，看的不是它成功时多惊艳，而是失败时用户能不能在五分钟内知道：发生了什么、卡在哪、下一步做什么、要不要自己接管。答不上来，它还算不上产品。</p>
      <p>所以每个 Agent 任务我都会配五样东西：状态机（可取消、可重跑）、每步预算、质量门禁、人工在环、全过程留痕。这些东西在 Demo 里全是成本，在上线后全是价值。</p>

      <h2>自主性的边界：按步骤给，不按产品给</h2>
      <p>做 Agent 产品有两种极端：一种把「全自主」当卖点，用户不敢用；一种把每一步都做成确认框，用户点到崩溃。我的做法是把自主性当旋钮，按步骤分配。</p>
      <p>可以自主的，是低风险、可验证、可回滚的步骤：检索、起草、内部整理。必须确认的，是对外发布、付费、删数据、代表用户对外沟通。判断变量有三个：容错空间（错了会怎样）、可验证性（能不能客观判断做对了）、成本敏感度（一次任务的钱是否必须可预期）。三个都宽松，可以放开；任何一个严格，就要把步骤做成可解释、可兜底的。</p>
      <p>模型能力每半年变一次，今天的边界明天会松动——今天必须人工确认的步骤，半年后可能可以全自动。但「把不确定性装进一个可交付的产品」这件事不会变，这也是 AI 产品经理真正稀缺的能力。</p>
      <p>最后说边界：受控工作流不是教条。创意类任务过早加门禁，会把质量压平；门禁过多，产品会显得很笨。什么时候该放手、什么时候该拦住，要靠场景判断，不能照搬原则。</p>
