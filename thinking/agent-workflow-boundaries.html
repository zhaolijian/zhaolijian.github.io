把 Agent 当受控工作流来设计

2026-10 · 约 1700 字

今年「Agent」成了 AI 产品里最容易被滥用的词：接一个大模型、加几个工具调用、写一句「自主规划」，就敢叫 Agent。但真正做过 ToB 或内容生产场景的人会知道，「自主」恰恰是这类场景最不敢要的东西。

我在做 GEO 内容生产链路时的选择是：把它设计成受控工作流，而不是一个追求全自主的 Agent。这篇文章讲清楚为什么。

全自主 Agent 在真实场景里的三个坑

  1. 不可预测：同一段输入，两次运行可能走完全不同的路径。对内容生产来说，这意味着质量不稳定、无法复现，用户不敢把结果直接交给客户。
  2. 成本不可控：模型调用次数、工具调用深度、重试次数都可能在某次任务里突然放大。ToB 产品必须能提前算清一次任务的成本上限。
  3. 无法验收：如果 Agent 自己决定「什么时候算完成」，产品就失去了验收标准。用户付了钱，却不知道交付物应该长什么样。

这三个问题在 Demo 阶段都可以被「效果很惊艳」掩盖，但一到真实用户、真实成本、真实交付，就会全部暴露。

我的做法：状态机 + 预算 + 门禁 + 人工在环

把「写一篇可被 AI 摘录的文章」拆成两条流水线：预检与生成。每条流水线都做四件事：

  • 状态机管理：任务从创建、执行、失败、重试到完成都有明确状态，可取消、可改稿、可重跑；
  • 每步预算：预检任务有墙钟上限与模型调用预算，生成任务有共享的调用上限；配图、质量复查也有各自的次数限制；
  • 质量门禁：预检有硬门禁（不通过就不进入生成），生成后有质量复查（不合格打回修补），同步前还有 readiness 检查；
  • 人工在环：用户可以在任意阶段打断、修改、重跑；所有中间结果留痕，任务可复现、成本可核算。

我不追求「让 AI 更自由」，而是让每一步可观测、可干预、可回滚。对产品来说，可控性本身就是价值。

什么场景适合全自主？

受控工作流不是唯一答案。判断要不要放开自主性，我通常看三条：

  • 容错空间：错了会怎样？代码补全错了可以撤销，内容发错了可能损失客户信任；
  • 结果可验证性：能不能用客观标准判断「做对了」？能，才敢让 Agent 自己迭代；
  • 成本敏感度：一次任务的成本是否必须可预期？ToB 交付基本是「必须」。

三条都宽松时，可以放开自主；任何一条严格时，就应该把工作流设计成「可解释的步骤 + 可兜底的失败」。

产品经理在这件事里的职责

Agent 产品的产品经理，工作重点不是「调 Prompt」，而是把不确定性变成产品行为：

  • 定义「什么算完成」——验收标准先于实现；
  • 设计「失败了怎么办」——重试、降级、让用户接管，而不是直接报错；
  • 让过程可见——用户要知道现在走到哪一步、大概还要多久、花了多少成本；
  • 把能力边界写清楚——哪些是产品保证的，哪些是概率事件，必须分开讲。

我越来越觉得，AI 产品经理的核心竞争力不是「懂模型」，而是懂怎么把模型的不确定性装进一个可交付的产品里。这件事，工程背景帮了我很多，但判断标准仍然是产品标准：用户能不能用、敢不敢用、值不值得用。
